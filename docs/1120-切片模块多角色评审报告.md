## 4. 分角色详报摘要

### 4.1 架构师（终评 3.0：模块边界 3 / 配置模型 2 / 引擎可维护 3 / 前端架构 3 / API 契约 4 / 测试 3 / 扩展性 3）

- **P0 引擎双份分叉**：engines/slice.py 4975 行 vs slice-worker/engines/slice.py 4867 行，树内 diff 确认此刻已不同步；同步靠 hash 包下载（engine_update.go:93-100），无 CI 拦截。dedupe.py:210-228 用 AST 解析引擎源码提取 DEDUPE_PRESETS，重命名即静默回退空 dict。
- **P1 三后端分发器三胞胎**：worker|local|celery 签名几乎相同，local 反向 import celery 私有函数（slice_helpers.py:1448-1453）；收尾逻辑三份不一致风险高。建议抽 SliceDispatcher 接口，celery 列为长期淘汰项。
- **P1 前端单组件**：EpisodeDetail.tsx 4048 行、77 useState、12 Modal 全内联；按配置卡拆 SliceConfigPanels/* + useReducer 收敛。
- **P2**：clip_id 靠 `clip_{index}.mp4` 文件名约定关联（api/slice.py:1571-1585），引擎改命名即错关联；slice run/callback/retry 零测试。

### 4.2 性能工程师（终评 3.7：转码 4 / 缓存 2 / 并发隔离 4 / GPU 4 / IO 5 / 进度 3 / 常驻 4）

- **P0-1 钩子链每成品重建（核实属实）**：`for (name_key, variant) in assignments`（slice.py:4651-4656）→ 每次进 TemporaryDirectory（:4663）→ 全部钩子逐个 slice_segment 重编码（:4692-4694）→ concat 再重编码非 `-c copy`（:4703-4709）→ tmp 随循环销毁。量化修正（第 2 轮自我纠错）：编码素材比钩子链:本体 ≈ 85:15，缓存后 100 成品 ≈ 45-50min（一次性链构建 ~3min），有后处理时地板 ~1h。
- **P0-2 成品后最多 6 次串行全片重编码**：字幕打码（:4777-4823）→ 烧字幕（:4830-4848）→ 水印打码（:4855-4861）→ 图片角标（:4864-4872）→ 文字角标（:4874-4879）→ 封面（:4881-4885），每个独立 ffmpeg 全时长 decode+encode。开启字幕+角标+封面的任务同一像素被编码 4-7 次。
- **P0-3 进度唯一打点=成品完成**：引擎全文件仅 3 处 PROGRESS（slice.py:4891/4326/4894），Go 仅解析 PROGRESS/OUTPUT 两种行（task_executor.go:404-427）无 ffmpeg `time=` 解析；叠加容器模式接线缺口（见裁决 #2）。
- **P1**：160% CPU 超订（compose:571,608 + threads=cores×0.8 slice.py:531-545）；100 成品串行上传（worker.go:830-853）；stuck 30min 误杀（config.go:79 + worker.json:16 烤进镜像，单成品 >30min 必被 kill 重投，MaxRetries=2 耗尽置 failed）。
- **GPU 现状**：三重探测设计好（SLICE_ENCODER 覆盖→静态表→实编 1 帧，slice.py:800-842 + 运行时回退 :740-769），但 163 无 GPU 实跑 libx264；烧字幕强制 libx264（:1913-1918 注释自述兼容性）。

### 4.3 UX 设计师（终评 4.0：信息架构 4 / 配置负担 2 / 引导 6 / 冲突呈现 5 / 进度反馈 2 / 新手 4 / 布局 5）

- **P0-1 进度假死（修正后口径）**：slice 引擎粒度=每成品（有效间隔分钟级）+ Remotion 队列等待窗钉 1% + 下载 0→100 跳变 + processing 状态在任务列表不画进度条（SliceTasks.tsx:446 仅 running/pending）、cancel/retry 双拒——真正的「三无死角」。
- **P0-2 七卡全展开**：右列竖屏转横屏/高光识别/源字幕打码/恒定水印打码/固定文字/角标/动态文字水印 7 个内嵌 Card 常驻展开（grep Collapse=0），小屏堆叠后更长（EpisodeDetail:4030-4045 Col md={12}）。
- **P0-3 跨入口能力缺失（质证升级）**：SliceTasks「新建切片任务」payload 完全没有 hook/highlight_mix/remotion 字段（grep 0 vs 90），用户在详情页学会的能力到任务页静默失效。
- **P1**：8 组视觉/去重配置无预设，换剧重调 8 个 Modal ≈ 40+ 字段；冲突矩阵只有 3 处点状提示无聚合视图；BatchSlice 要求手写 JSON（BatchSlice.tsx:715-731）。
- **引导是亮点**：65 个 Tooltip（覆盖 47%）+ 状态驱动 workflowGuide（:1771）+ WORKFLOW_STEPS 6 步——分数为四方最高单项（6 分）。
- **双模式方案**：简单模式 6 件事（切片模式 Cascader:2309 / 输出档位默认 auto / 钩子选择器+混搭三小项 / 高光混剪 Switch / 视觉包装三档单选 / 开始按钮），专家模式右上角开关、同一 state 切换不丢配置，冲突摘要两种模式常驻。

### 4.4 SRE（终评 4.3：状态机 5 / 失败恢复 4 / 可观测 4 / 部署 3 / 资源 4 / 数据 4 / 安全 6）

- **P0-1 direct queue 丢任务级联**：FetchDirectTask 注释自认「弹出即确认无需 XAck」（redis_client.go:207-217），claimLoop 只扫 Stream（worker.go:476-499）；beat 无切片任务 running/pending 巡检（celery/tasks.py:89-157）；闸门只数 running/pending（slice_helpers.py:1038-1062）→ 崩溃级联 429 全局封死。建议巡检用 Redis lease/started_at 判活而非 DB started_at（Go 重投只重写 Redis hash :729-734）。
- **P0-2 processing 无出口**：cancel 门 pending/running（api/slice.py:1943-1947）、retry 门 failed/cancelled/completed（:1723），Remotion 路径置 processing（:1290）两门全关；stale recovery 路由到 remotion 队列（tasks.py:87-88）与被守护的 worker-remotion 同队列同 profile 开关（compose:414）。
- **P0-3（新发现）容器模式进度接线缺口**：main.go:100-102 Printf-only；结构性后果＝单成品 >30min 必被 stuckTaskLoop 误杀（worker.go:563-609）。修复与 UX 进度假死是同一处改动。
- **P1**：Remotion 1h 超时误杀长渲染（REMOTION_RENDER_TIMEOUT_SECONDS=3600，config.py:320；实测 combine 可跑 5h）+ 完成回写不检查状态可翻转已取消任务（remotion_tasks.py:163-200）；镜像全 :latest 无回滚（compose:15,302,551）；sync-engines「忘了=没改」陷阱（deploy.sh:164 有跑但手动 scp 流程不会）。
- **安全基线尚可（6 分）**：.env gitignore、密码 24+ 位、回调 per-task token（slice_helpers.py:1740-1750）；扣分点：heartbeat/引擎包 internal_router 无鉴权（workers.py:136,682-688）。
- **「还能卡死吗」三条路径**：①BRPOP 丢失+闸门级联（实证）；②processing 无出口+recovery 同队列（实证）；③「行已提交、消息未发」窗口 backend 重启留 pending 悬挂（推断，无巡检回收）。

## 6. 评审期间现场变动（Addendum，2026-11-20 深夜）

评审进行期间，一个**并行会话**在主仓落了 7fe2e25 并写入了接力包 F9（b05a845e 任务被 stuckTaskLoop 误杀，诊断为引擎 stdout 块缓冲吞掉 PROGRESS 心跳，修复＝Go 侧 `task_executor.go:91` 加 `-u` + 引擎侧 `slice.py:4096` line_buffering，已部署双 worker）。主审对修复完整度做了端到端复核：

**已修复的半边**：PROGRESS/OUTPUT 行不再被 8KB 管道缓冲吞掉，能及时到达 Go 进程（parseEngineLine）。

**未修复的半边（本报告 Top1 的核心，复核实锤）**：
- 容器 CMD 固定 `--no-tui`（slice-worker/Dockerfile:109）→ `runDaemon`（main.go:86）→ SetCallbacks（main.go:96）＝纯 Printf；TUI 模式（main.go:133）也只发 Bubbletea UI 消息。
- 引擎每成品的 `PROGRESS:N` 行走 `parseEngineLine`（task_executor.go:412-413）→ `te.onTaskProgress` → `w.onTaskProgress`（＝Printf），**从不经过 emitProgress**。
- `LastProgress`（卡死检测心跳）只有两个刷新点：任务启动 worker.go:703 + emitProgress 内部 :1167；emitProgress 只在阶段边界被调用（753/761/818/825/828/841/853）。
- `stuck_task_minutes: 30` 烤进镜像（Dockerfile:94 COPY worker.json → worker.json:16），compose 无环境变量覆盖。
- **结论：引擎段（ffmpeg 0→100 之间）静默超过 30 分钟的长任务，今天（7fe2e25 之后）依然会被 kill 重投**。7fe2e25 的实证「重试任务 ~100s 内进度即达 worker（docker logs [ffmpeg] 1%）」走的是 Printf 日志路径，不等于心跳/Redis 路径；对引擎段 <30min 的任务（如快速模式）自然无事。**若并行会话的后续验证只看 docker logs，会把「未修完」误判为「已修复」。**
- 同根的 UI 现象也不变：后端/前端只能看到阶段边界 0/100，100 成品任务运行中依旧钉在 0-5%——引擎明明每成品都在打印 PROGRESS，只是接错了线。

**建议的收尾动作（与并行会话协调，勿重复动手）**：把 worker.go:113-114 与 :118-122 两处 `SetProgressCallback` 的回调体从 `w.onTaskProgress(...)` 改为 `w.emitProgress(taskID, phase, percent, detail)`（transfer 用 "transfer" phase、executor 用 "ffmpeg" phase）；`w.onTaskProgress` 保持纯日志用途。**不要**把 onTaskProgress 直接接到 emitProgress（emitProgress 内部首行就调 onTaskProgress，会无限递归）。验收判据：①UI 进度随成品数推进；②人为构造 >30min 静默段的任务不被杀；③stuck 误杀只应命中真挂起的 ffmpeg。
