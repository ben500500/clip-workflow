## 1. ① 导入并入 ① 脚本库，页签少一个

上一版把「导稿」单独做成一个页签，用户的意见是那一小行功能块不值得占一个 tab。现在 ① 屏的结构是：

```
① 脚本库
├── 导入（Card，最上面）    导入钩子视频并反推 ／ 上传脚本文件 ／ 手写脚本
├── 待过审（有审核职能才显示）
└── 脚本表  预览｜脚本｜原型｜状态｜已投｜(谁的)｜收藏｜操作
```

「导入」这张卡的标题就写「导入」两个字，不再有「先弄到稿」这种自造词（`SimpleLibrary.tsx:725`）。原来那个「① 导稿」页签的 children 整体搬进来了，功能一项没少；`tab` 状态只剩 `'scripts' | 'produce' | 'outputs'`（`:1067-1069`）。

门禁同步改了：A2/A3 从「恰 4 个」改成「恰 3 个」，A4 判 ① 屏顶部卡的标题以「导入」开头且同屏有「改稿」，且明确判 `!/先弄到稿/`。

## 2. ② 「我的」冒出别人未定稿——真因是漏传参数，不是隔离逻辑错

用户看到的「未定稿的即使不在我的收藏里也会展现」，查下来 defect 不在后端的 owner 口径：`GET /api/assets/scripts` 的 `me` 侧一直是「我写的 ∪ 我收藏的」，并且和 `carrier_status` 是**同一条 conds 列表里 AND 起来的**（`misc.py` 列表口）。

漏的是 ① 屏那个「待过审」小区块——它自己调 `listScripts`，参数里写了 `carrier_status: 'pending'` 却**没写 owner**，所以顶栏「仅看自己」翻成开、主表收住了，这一块仍然全量取，别人的 draft 就从这里冒出来。修法是一行：

```ts
// SimpleLibrary.tsx:242
const res = await assetApi.listScripts({ owner, carrier_status: 'pending', page_size: 100 });
```

`owner` 进了 `fetchPending` 的依赖数组（`[canReview, owner]`），开关一翻就重取。

两层门禁钉住它，因为界面肉眼很容易看不出来（截图上主表是对的，只有小区块多几条）：

- CDP **T3e**：抓网络日志，要求带 `carrier_status=pending` 的请求**每一条**都同时带 `owner=me`（漏传即红）——判的是底层请求参数而不是屏幕上少了几行；
- pytest `test_my_view_pending_filter_does_not_leak_others_drafts`（`:13897`）：后端直接建两条 draft（自己的＋同事的、同事那条当前用户没收藏），断言 `owner=me&carrier_status=draft` 只回自己那条。这条在当前后端**改前也是绿的**，它的定位是口径防回归（防止后面有人把 AND 改成 OR 或另开一条不带 owner 的分支），不是本 bug 的复现证据——真复现证据是 T3e。

## 3. ③ 抽屉给全文＋点标题直接开

列表口为了不把几十条正文一起拖过来，只回 `preview`（**正文前 100 字**，`misc.py:15585` `preview = " ".join((r.body or "").split())[:100]`）＋`body_chars`（全文长度）。所以「列表里看着有内容、打开是空的」是接口分工，不是取数失败——但界面不能让人自己猜。

现在 `ScriptEditorDrawer` 打开时按 id 打一次详情口 `GET /assets/scripts/{id}` 取全文（`:101`）：

- 全文到达前：表单**禁用**，字数计数器显示「正文读取中…」（`:214`），顶部一行 Alert「正文读取中，取回来之前先别保存（免得把没看到的正文当成空的）」（`:242`）；
- 取全文失败：明确报错并且**拦住保存**（`persist()` 在 `loadingBody/bodyError` 时直接回 null），否则很容易把「我没看到正文」写成「正文清空」；
- 改稿比对基准换成取回来的那一行（`row = full ?? script`），不是列表行——拿列表行当基准会把「没改」误判成「被清空」。

点标题打开：表格「脚本」列（`SimpleLibrary.tsx:587`）的标题改成 `<Link onClick={() => setEditor({open:true, script:r})}>`（`:593`），和行尾「打开」按钮同一个入口。「待过审」那张小表的脚本列（`:877`）保持纯文本——那本来就是给审核员看的，不需要就地改稿。

CDP 里 X 段的判据是**两个实测值比大小**：抽屉字数 > 列表那一格显示出来的字数。上一版这里写死了「>100」，第一跑判成假红——因为种子的正文只有 87 字，两头都短于 100 时这个判据是空的。改成「列表给人看到的字数」与「抽屉里的字数」现场各取一个再比大小，既真又稳（种子也已加长过 100 字，见 §5）。

## 4. ④ 豆包失败重试：做不到「要多少收多少」，给的是有界重试＋明确缺口

先给结论（这条用户直接问了能不能）：**不能保证百分百回收**。两个硬约束——

1. 每次重启都是同一条 payload 再上一次板，**消耗的是号池真实额度**；失败原因板面上不给（失败行没有原因字段），机器分不清「拥堵等一下就好」和「这条稿子就是出不来」。
2. 「补到 N 为止」会把同一条在拥堵那天烧十几遍；出轮询窗口再补就是隔夜自动补投，那条口径没开（和 `ASSET_BOARD_POLL_MAX_MINUTES` 是同一条纪律）。

所以按用户选的口径做**有界自动重试＋缺口提示**（AskUserQuestion 选项「有界自动重试＋缺口提示（推荐）」）：

| 环节 | 现在的行为 |
|---|---|
| 自动重试 | 只在**本次轮询窗口内**；只救「整批全版失败」的单；次数由 `ASSET_BOARD_RETRY_MAX` 定，默认 **2**（首投＋2 次＝最多 3 次上板机会），填 0 完全关掉、填 1 回到旧口径 |
| 不重试 | `recover_only`（接续回收）永不重试（tracked 行 `allow_retry: False, payload: None`，`misc.py:10717`）——它已经不在开单现场，自动补投等于隔空花钱 |
| 部分失败 | **立刻收敛**并把缺口点名，不重烧整条（`:11390` 的分支条件里 `got` 非空即不进重试） |
| 缺口账 | 逐张 `short_by = board_total − 库里产物数`（`:11544`），只在 PR_SUCCESS／PR_FAILED 行给；整批聚合 `gap = {expected, collected, short_by, retry_max, retries}` |
| 人怎么补 | 生产单这行「操作 → 按同文案重开单」，只补差额 |

缺口账是**读侧推导**（`board_total` 减 `AssetOutput` 计数），没有新列、没有迁移。序列化在 `asset_serializers.py` 的 `_serialize_production` 里，`status in (PR_SUCCESS, PR_FAILED)` 才给 `short_by`，避免回收途中满屏「缺 N 版」的假告警。

界面两处说人话：

- 开单回执消息（`misc.py:10834-10887`）拼上「失败自动重启 N 次…」＋ `_gap_hint()` 那句：「；缺口 N 版（要 X 版、账上已收 Y 版）：自动重试只在本次轮询窗口内、且只救整批全失败的单，部分失败的缺口请到生产单对这行点「按同文案重开单」补投——隔夜不自动补投是定死的口径」；
- 完整模式生产单「成片」列（`AssetProductionPanel.tsx:1463-1487`）：「已收 N 段／还没收片」＋ `缺 N 版` 橙色徽标，浮窗写清补法。

用例：`test_dispatch_restarts_a_failed_task_within_the_retry_budget`（`:6962`，retry_max 取 2/1/2/0 四种边界，含「用完额度不再烧第四遍」）和 `test_dispatch_partial_version_failure_converges_with_a_named_gap`（`:7034`，`_FakeBoard(fail_tids={"T000002"})` 断言只上板 1 次、gap 字典数值、消息里那句提示）。
