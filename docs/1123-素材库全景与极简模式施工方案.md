# 第一部分 · 素材库整体情况

## 1. 它是什么，在系统里占哪一格

素材库是 clip-workflow 里的**一条独立业务线**：把"短剧推文的生产输入"（钩子视频、原片、角色卡图片、文案）当资产管起来，再一路推到豆包出片、成片交付。它和仓库里另一条更老的线（视频号切片 / 一键切片 / 双配混拼）**并行存在、共用引擎但互不隶属**——两边同名不同物是新人最容易踩的坑（见 §7 风险）。

一句话链路：**导入 → 反推/出文案 → 审核 → 投产（投豆包板）→ 成片墙（交付包）**，业内简称"五环"。〔file:line：五环定义在 `frontend/src/components/assets/StepGuide.tsx:206`〕

## 3. 数据模型逐个说清

〔file:line：`backend/app/models/asset.py`〕

**`asset_categories`**（:251）— 单层原型字典，无层级、无父子。读全员、写仅 admin；下线不删行（`GET/PUT /assets/categories` 是**整单语义**，一次提交全表）。纯人工点选，不自动分类。

**`asset_batches`**（:279）— 一次导入/一批产物的容器，`created_by`＝导入人。是跨人闸门（"替他人批次花钱"）的判据锚点之一。

**`asset_items`**（:314）— 素材本体。三组正交的列值得单列出来：

- **四阶段闸门列**：`stage_import / stage_prompt / stage_summary / stage_produce / stage_compose`——五环每一环在素材行上留一格状态，前端"进度"和 0 元拼接的可行性判断都读这里，不靠运行时推断。
- **成本列**：`cost_prompt / cost_produce / cost_parse`，是**按档位推算的额度**（智令不逐单回传金额），用于对账，不是账单原文。〔file:line：`assets/misc.py:20-31` 成本口径注释；11-23 拆分后行号与旧 `assets.py` 同源一致，但**路径必须写 misc.py**〕
- **分流列 `media_kind`**（0059）— 全链路**唯一**的视频/图片分流依据：图片在四个 stage 全记 `skipped`、终态 `image_ready`、**不计费不抽帧**；采集侧那两个"视频白名单"永远不加图片。这条是批 G 定的规矩，改动任何校验都要先看它。
- 另有 `play_url` / `play_url_at`（0062 播放直链缓存，TTL 6h）与 `download_status`。

**`asset_summaries`**（:410）— 一条钩子文案（候选）。要点：

- `asset_id` 是 **NOT NULL + ondelete=CASCADE**〔:427〕——素材一删，文案随之消失。**这条约束直接否掉了"把脚本挂在文案表上"的方案**（见 §8.1 为什么要新表）。
- 状态列叫 **`audit_status`**（pending/approved/passed_edited/rejected/need_rewrite），不是 `status`；只有 `reviewed_by`（过审人，过审写、撤审清），**没有 `created_by`**——所以"个人的"这个语义在该表表达不出来。
- `text_before_edit` 存"改后重提"的改前原文，配合 `resubmit_note` 和 AuditLog 构成驳回闭环。
- `risk_hit`／`consistency_ok`／`is_recommended`／`hook_code`／`doubao_prompt`／`prompt_preview`＋`cost_preview` 是六个业务闸门字段。

**`asset_productions`**（:514）— 一张生产单＝一次投豆包（或一次拼接）。列很多，分四组读：

- 内容：`prompt_text` / `prompt_snapshot` / `doubao_prompt` 派生列 / `variant_basis` / `drift`＋`drift_reason`（换皮后与角色漂移留痕）/ `video_titles` / `project_title` / `seq`
- 板面：`board_tag` / `board_date` / `board_name` / `board_total` / `board_tid` / `board_rgid` / `board_last_status` / `board_last_check_at`（批 L 新加的**投放进度写回**，前端显示"出片中·HH:mm 查"）
- 卡：`character_card_key`（老的单卡 key，已知有坑）/ `card_asset_ids`（0060，**数组顺序＝板上 picDatas 顺序＝主形象**）
- 拼接：`concat_asset_id` / `concat_order` / `concat_last_result` / `is_trial`
- 幂等与状态：`idempotency_key` / `attempts` / `provider_task_id` / `celery_task_id` / `status`（queued/running/success/failed/order_ready/superseded/cancelled/skipped）

**`asset_outputs`**（:623）— 产物行。`kind` 目前只有 `doubao_raw`，schema 已留 `composed`（`composed_from_output_id` 列在）。带 `qc_status`/`qc_result`/`qc_note`（质检留痕）、`sha256`、`resolution`、`expires_on`、`board_out_url`、`downloaded_at`。

**`asset_frames`**（:695）— 抽帧图，两侧归属：素材侧（`asset_id`）与产物侧（`output_id`）。幂等靠**两条部分唯一索引**（各自侧幂等），不是照计划里那条 `UniqueConstraint`——那条会被"同素材多产物"撞死，批 E 现场改的。`cover_image_key` 也在批 E 补上了写入方。

**`asset_jobs`**（:790）— 后台任务台账（批 C 的 D-1）。**这是链路里第一个后台任务**，跑在 backend 进程内 asyncio 协程（**不是 Celery**），提交即回 job 号。设计动因：同步等模型会顶穿超时链（见 §5.4）。

**`asset_element_guesses`**（:831）— 换皮参数的自动猜测缓存，幂等键 `UniqueConstraint(body_hash, slot_key)`。现网 152 行。

### 5.3 风险词与一致性

三层结构：默认词库 → 环境覆盖 → 生效值，`GET/PUT /assets/risk-lexicon`（读全员、写仅 admin，改词**保存即生效不发版**，TTL 300s）。block 级命中是**硬闸门**：形态不合规＋命中 block 词的稿子，"改后重提"也照样拦（一致性不过只留痕不拦）。PUT 带 `asset.risk_lexicon.update` 审计；级别键拼错从"静默丢词"改成报错。导出前按当前词表**重扫**，admin 强行导出必须带理由并进审计（R-4）。

### 5.4 超时链（外到内严格递减，相邻两层不许同值）

```
根 nginx 3600s  >  frontend nginx 1200s  >  浏览器 MODEL_WAIT_TIMEOUT 960s  >  后端同步口 900s  >  autoclip API_TIMEOUT 600s
〔nginx.conf:97-98/127-128〕   〔frontend/nginx.conf:34〕      〔misc.py:4409 注释〕        〔misc.py:4409〕
```

批 C 的 **D-1 队列化**是这套超时链的根治口：四类后台任务里投板（`dispatch`）是**默认就走后台**的那一类〔misc.py:10057〕，其余同步口靠 `async_mode` 参数切换。`misc.py:576` 的注释钉住了规矩："false 只留给后台协程与回归用例"。

### 5.5 闸门的真实强度（必读，别被"已自动化"误导）

后端闸还在：反推 ≥2 条必须 `confirmed=true`〔misc.py:3867 区，评审记录 `assets.py:3867`〕，投板必须"我已逐批确认"＋admin 强行需填理由。但 11-12「钱面下架」（`a0d8a95`）之后，**前端恒发 `confirmed: true`**〔`AssetListPanel.tsx:339/490/621`、`AssetProductionPanel.tsx:1075`；:409 注释自陈"按钮本身就是那一下人工确认"〕。

也就是说：**现存保护是"一批一次点击"，不是"逐条知情"**。极简模式不会削弱它，但任何方案（包括本文）都不许把它表述成"已有自动闸门"。屏 2 那一下轻量过审的价值，恰恰是把这个隐形点击**变成一个有名字、有审计的按钮**。

`GET /assets/audit-logs`＋`AuditLog` 表：改前原文（`text_before_edit`）、谁点的、admin 撤审抽检全在链上。风险词库改动、导出强放、跨人花钱均写审计。

## 9.1 数据模型增量

> `state='ready'` 收）逐条写在 **§11.4**；下面这段保留作设计推导原文，别当现行口径读。

### A. 新表 `asset_scripts`（S1）

为什么必须新表而不是复用 `asset_summaries`〔file:line〕：`asset_id` NOT NULL＋CASCADE〔`models/asset.py:427`〕会让素材一删稿子即消失；且该表只有 `reviewed_by` 没有 `created_by`，"个人的"表达不出来。

```
asset_scripts
  id                    UUID primary
  owner_id              UUID  NOT NULL           -- 「个人的」锚点（summaries 缺的就是这个）
  name                  VARCHAR(60) NOT NULL
  body                  TEXT    NOT NULL
  state                 VARCHAR(12) NOT NULL     -- 'draft' 库稿 | 'ready' 可投稿   ←拍板①
  category_id           UUID  NULL FK asset_categories
  source_kind           VARCHAR(12) NOT NULL     -- 'reverse' | 'upload' | 'manual'
  origin_asset_id       UUID  NULL FK asset_items  ON DELETE SET NULL
  based_on_script_id    UUID  NULL FK asset_scripts ON DELETE SET NULL  -- 派生链，不改写原文
  body_hash             CHAR(64) NOT NULL
  note                  TEXT NULL
  created_at / updated_at
  部分唯一索引 (owner_id, body_hash) WHERE body_hash IS NOT NULL   -- 幂等，照 AssetElementGuess 抄
```

设计要点：`based_on_script_id` 让"库稿→可投稿"是**派生**而不是覆盖，出处链永不断（审计与"用别人的脚本投产"责任归属都靠它，沿用 `ProduceRequest.cross_person_confirm` 口径）；`origin_asset_id` SET NULL 保证素材删了脚本还在（这正是它不进 summaries 表的原因）。建表靠 `create_all` 自动建〔`app/database.py:455`〕＋一条 `00xx_asset_scripts.py` 迁移给现网补 stamp。

### 11.4 `asset_scripts` 定稿结构（对 §9.1A 的修订）

```
asset_scripts  〔models/asset.py:861；迁移 0075；PG 侧实体验证见 §11.7〕
  state VARCHAR(12)  -- draft 库稿 | ready 可投稿 | retired 已下架      ← 缺口 2：三态
  carrier_summary_id UUID NULL FK asset_summaries ON DELETE SET NULL   ← 新增：生产载体回指
  部分唯一索引 uq_asset_scripts_ready_body (owner_id, body_hash) WHERE state='ready'
```

- **缺口 1 按推荐 (a) 落地**：finalize 一字未改＝**复用同一行**转 `ready`（不插新行、`based_on_script_id` 留空）；
  索引只约束 `ready` 行——草稿允许重复（派生草稿在改字之前与母稿逐字相同是正常状态），
  定稿时内容与已有定稿相同则幂等返回那一行、这条草稿随之收起；并发窗口由索引兜底（撞索引 → 409 指回已有那条）。
- **定稿即冻结**：`ready` 行正文不可改；PUT 到非 draft 行一律**派生新草稿**（`based_on_script_id` 指回原稿），
  原稿一字不动 ⇒ 投出去的永远是对得上号的那一版。派生不问人（读全员可见，§9.1C）。
- 下架＝软删（`retired`）：被生产单引用过的脚本硬删会让"谁用哪一版投的片"查不回来。

### 12.4 实测才露出来的一个真问题（P2；**未动代码，等用户定**）

**组合产物的文件名会套娃，且套到第三层起正片名被截掉。** 命名是
`钩子·<钩子片名>×<正片名>`〔`misc.py:13320`，钩子侧塞的是上一层**整名**〕，
而组合产物自己又能当钩子用 ⇒ 每拼一层就把上一层整名原样塞进去。本机连跑三轮实测：

```
第 3 轮（79 字符 / 186 字节，距 80 字上限只剩 1 格）
钩子·钩子·钩子·横屏实测×钩子·8RZZ1×三岁女儿装棺推下悬崖.mp4×砸碑建陵园托梦替嫁.mp4×砸碑建陵园托梦替嫁.mp4×砸碑建陵园托梦替嫁.mp4
第 4 轮（_safe_matrix_name 的 [:80] 生效，被切掉的正好是尾部最新的正片名）
…×砸碑建陵园托梦替嫁.mp4×砸碑建   ← "砸碑…" 之后整段丢失
```

三条边界核过，**不是**文件系统事故：上限 `[:80]` 个字符＝最坏 240 字节，`.mp4` 是**截断之后**才拼的
（`misc.py:12574`），所以扩展名永远完整、单段路径名 ≤244 字节 < ext4 的 255。
所以这是**可读性/可辨识**问题：一线在成片墙看不出这条拼的是哪部正片，前缀全是"钩子·"噪音。
两条候选修法（都很小，等口径）：① 钩子侧像正片那样只取末段（`split("·")[-1]`）；② 干脆用"钩子编号×正片名"，不塞片名。
