# 剧目管理设计方案（基于去空行筛选表）

> 版本：v1.0 评审稿 ｜ 2026-08-18
> 数据底座：`【平阅科技】视频号漫剧信息总表_去空行.xlsx`（Benny 提供的筛选版，共 44 条，`漫剧总表` Sheet，10 个字段）
> 关联：ISSUE #130「视频号自动发布」；沿用 v3.1 多运营者方案的技术约定（UUID 主键、MinIO object key 存图、RBAC data_scope 过滤、审计链路）

---

## 〇、TL;DR（评审速览）

在 clip-workflow 现有「smart_import 两段式导入 + PublishTask.material_id 预留 + 短片制作发布素材生成」基础上，**新增一套剧目主数据（Drama）模型**，做到：

- **可导入**：按筛选表的 10 个字段 + 自定义扩展字段，导入时对「同名称剧目」做 **diff 预览 + 询问确认**后再更新；
- **可关联**：视频号详情（VideoAccount）可绑定剧目，支持一剧多号；
- **可联动**：视频号发布时，以「剧情简介」为入参调用现有 `/shortdrama/publish-material/generate` 生成发布素材（短标题/配文/话题/神评）并挂到 `PublishTask.material_id`；
- **可运营**：剧目库支持按 男/女频、题材、评级 筛选统计，封面/剧照走 MinIO。

> **关键澄清**：与「视频号 v3.1 方案」类似，本方案推荐**先出设计评审、再分 Phase 落地**，避免一个 PR 过大。本文档即评审基线。

---

## 一、数据底座核实（以筛选版 44 条为准）

Benny 之前提供的原始表为 5748 条；本次明确以**去空行筛选版（44 条）**为唯一数据底座。对筛选版逐列分析：

| 字段（表头） | 类型 | 本表取值 | 设计落点 |
|---|---|---|---|
| `漫剧名称` | 文本 | 44 条唯一 | 主键去重核心（Drama.name，唯一索引） |
| `更新日期` | 日期 | 2026-08-13 ~ 08-18 | Drama.updated_date |
| `男/女频` | 枚举 | 男频 12 / 女频 32 | Drama.frequency（枚举） |
| `题材` | 多值标签 | 37 种组合（家庭/都市/婚姻/言情/反击/逆袭…） | Drama.tags（JSON 数组，多选标签） |
| `漫剧类型` | 枚举 | 全部 `AI真人剧` | Drama.type（枚举，预留 AI真人剧/真人剧/动漫…） |
| `上架状态` | 枚举 | 全部 `已上架` | Drama.listing_status（枚举：草稿/待上架/已上架/已下架/归档） |
| `上架日期` | 日期时间 | 2026-08-13 ~ 08-18 | Drama.listed_at |
| `评级` | 枚举/可空 | 新剧A+ 30 / 新剧S+ 10 / 空 4 | Drama.rating（可空枚举） |
| `素材链接` | URL | 44 条百度网盘（含 pwd） | Drama.material_link（**去密码**存主表，密码字段脱敏，见 6.3） |
| `上架账号` | 文本 | 全部 `海漫剧场` | 关联 VideoAccount（DramaAccount 多对多，见 2.2） |

> **本表口径**：44 条全部属于「海漫剧场」一个账号、全部「AI真人剧」、全部「已上架」。因此本筛选版的 `上架账号` 实际是**单账号**，但设计上仍按**一剧多号**建模（见 2.2），兼容未来多号上架的通用场景。

## 二、表结构设计（主表 + 子表，避免一张大表）

沿用 v3.1 的「避免把图片/多值塞进一张大表」原则，拆 4 张表：

### 2.1 主表 `dramas`（剧目）

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | UUID PK | 主键（沿用现库全 UUID） |
| `code` | String(20) **唯一** | 运营可读的唯一剧目 ID，生成规则 `DR-<8位大写HEX>`（如 `DR-0A3F9C2E`），见 6.1 |
| `name` | String(200) **唯一索引** | 漫剧名称（去重核心） |
| `frequency` | String(20) | 男频 / 女频（枚举） |
| `type` | String(30) | 漫剧类型（AI真人剧/真人剧/动漫…） |
| `tags` | JSON | 题材多选标签数组（如 `["都市","反击"]`） |
| `rating` | String(20) nullable | 评级（新剧S+/新剧A+/SS+/空） |
| `synopsis` | Text nullable | **剧情简介**（自定义扩展字段，用户输入，也是发布素材生成的入参） |
| `cover_file_key` | String(500) nullable | **剧目封面**（MinIO object key，图片类型） |
| `listing_status` | String(20) | 上架状态（草稿/待上架/已上架/已下架/归档） |
| `updated_date` | Date | 更新日期（表内） |
| `listed_at` | DateTime nullable | 上架日期（表内） |
| `material_link` | String(1000) nullable | 素材链接（百度网盘，**去除密码**后存） |
| `material_link_pwd` | String(100) nullable | 网盘提取码（**单独字段 + 密文存储**，见 6.3） |
| `created_by` | UUID nullable | 操作人（R17 actor_id，审计用） |
| `operator_id` | UUID nullable | 号主（可选，当剧目归属某运营者时） |
| `created_at` / `updated_at` | DateTime | 审计时间戳 |

### 2.2 子表 `drama_stills`（剧照，一对多）

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | UUID PK | |
| `drama_id` | UUID FK→dramas | 所属剧目 |
| `file_key` | String(500) | MinIO object key（图片类型） |
| `sort_order` | Integer | 拖拽排序 |
| `created_at` | DateTime | |

### 2.3 关联表 `drama_accounts`（剧目 ↔ 视频号，多对多）

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | UUID PK | |
| `drama_id` | UUID FK→dramas | |
| `account_id` | UUID FK→video_accounts | 上架账号（VideoAccount） |
| `listed_at` | DateTime nullable | 该账号上架时间线 |
| `created_at` | DateTime | |

> **双向可查**：从「视频号详情选剧目」= 按 account_id 反查该号关联的剧目；从「剧目库看该剧在哪些号上架」= 按 drama_id 正查 accounts。与 `上架账号` 字段对应。

### 2.4 关联表 `drama_materials`（剧目 ↔ 发布素材）

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | UUID PK | |
| `drama_id` | UUID FK→dramas | |
| `material_id` | UUID FK→publish_materials | 该剧目生成过的发布素材记录 |
| `account_id` | UUID nullable | 若按号分别生成则带号（一剧多号一素材，见 5.3） |
| `created_at` | DateTime | |

> `PublishTask.material_id`（现模型已有，`models/publish.py:138`）在发布时直接指向 `publish_materials`，因此**无需改 PublishTask 表**；`drama_materials` 只是把「剧目↔素材」的对应关系独立记录，便于剧目库聚合展示。

## 三、导入流程（复用 smart_import 两段式 + 补 diff 确认）

Benny 的硬性要求：**「后期再次导入表格中有相同名称的剧目则更新该条剧目信息，需要在更新前列出相关内容并询问用户是否更新」**。

### 3.1 流程

```
① 上传 → ② 解析/去重预计算 → ③ diff 预览（新增/更新，逐条勾选）→ ④ 确认执行
```

- **复用** `dashboard.py` 的 `/dashboard/import/upload → /preview → /confirm` 三段式骨架（`backend/app/api/dashboard.py:612` 起）与 `DataImport.tsx` 前端映射 UI，但**新增一个剧目专用导入端点**（`/dramas/import/*`），不污染通用 smart_import。
- **新增 `/dramas/import/preview`**：返回三组
  - `new[]`：待新增（名称不在库中）；
  - `update[]`：待更新（名称命中，逐条给出**旧值 vs 新值 diff**）；
  - `unchanged[]`：名称命中且各字段一致（**默认跳过，可勾选强制覆盖**）。
- **新增 `/dramas/import/confirm`**：接收用户勾选的 `accept_new_ids[]` + `accept_update_ids[]`，仅对勾选项写入/更新；未勾选的**跳过**（不静默改动）。
- **幂等 & 可回滚**：写入前记录一条 `drama_import_history`（复用 `get_import_history` 模式），支持「误导入回滚到上一版本」。

### 3.2 去重语义（**写死**，P1）

Benny 要求「同名称剧目则更新」。为避免同名误判，去重键采用 **`name` 唯一索引**，但**更新判定**时仅以 `name` 命中即视为同一条待更新；若命中多条（同名异频极端情况），**退化为需人工选择**（返回候选列表）。在 44 条筛选数据上，`name` 全部唯一，因此当前无冲突；设计上保留「同名→人工裁决」兜底。

> 相比 v1 讨论里「名称+频+题材三元组」：由于本筛选表 `漫剧名称` 已全部唯一，主键用 `name` 即可，简化模型；冲突时再走人工。三元组语义作为**冲突兜底策略**记录在案（见 6.2）。

## 四、视频号详情关联剧目

- `VideoAccount`（`models/publish.py:26`）**不改表结构**，通过 `drama_accounts` 关联表反查剧目（见 2.3）。
- 前端「视频号详情」新增「关联剧目」区块：选择/移除该号上架的剧目，列表展示剧目封面、名称、评级、题材。
- 发布弹窗选号后，自动带出该号关联的剧目候选，供选择（联动见第五章）。

## 五、发布联动（剧情简介 → 发布素材）

Benny 需求：**「视频号发布时可以调用短片制作-发布素材中的接口，将剧情简介作为输入，生成相应配套的发布素材」**。

### 5.1 现有接口复用（全部现成，不改 autoclip）

- 后端：`POST /api/v1/shortdrama/publish-material/generate`（`backend/app/api/publish_material.py:121`），入参 `story`（剧情简介）+ 可选 `title/theme/tone/platform/extra_requirements`，输出 `material`（short_title / captions / tags / comments）。
- autoclip 侧：`autoclip/app/services/publish_material_generator.py:49` 的 `generate_publish_material(story, params)`，由 autoclip 的 `POST /api/v1/publish-material/generate` 承接。

### 5.2 发布弹窗「一键生成发布素材」

发布弹窗选择剧目后：
1. 自动带出 `Drama.synopsis`（剧情简介）填入 `story`；
2. 自动带出剧目 `tags`（题材）merge 进 `extra_requirements`，并作为后续发布话题（见 5.3）；
3. 点「生成发布素材」调 `/shortdrama/publish-material/generate`（`save=true`）；
4. 返回的 `record_id` 写回 `PublishTask.material_id`，且 `drama_materials` 记录 `drama_id ↔ material_id` 关联；
5. 结果（短标题/配文/话题/神评）**回填到发布表单**，运营可微调后确认发布。

### 5.3 话题标签贯通

剧目 `tags`（题材）在生成发布素材时作为 `extra_requirements` 提示，并在发布时 merge 进 `material.tags`，让「剧目库标签 → 发布话题」自动贯通，运营不用重复维护。

### 5.4 一剧多号一素材

同一剧目下多个视频号发布时，可一键复用同一套素材，或针对不同账号换不同配文版本（`drama_materials.account_id` 区分），避免每号重新生成。

## 六、关键设计决策（含 v1 讨论吸收项）

### 6.1 唯一剧目 ID 生成规则
- 建议 `DR-<8位大写HEX>`（如 `DR-0A3F9C2E`），运营侧肉眼可读、Excel 回填好对照。
- 生成方式：`code = "DR-" + uuid4().hex[:8].upper()`，入库前查唯一索引冲突则重抽。
- 备选：裸 UUID（与现库一致）。**默认推荐 DR- 前缀**，评审确认。

### 6.2 去重键语义
- **主键去重**：`name` 唯一。
- **冲突兜底**：`name` 命中多条时走「人工裁决」；同 `name` 但明显不同内容（异频/异题材）也在候选里标出，由用户判定新增还是更新。
- 三元组（name+频+题材）作为**进阶判定**写入 confirm 前的 diff 展示，帮助用户看清差异，但不作为硬性合并键。

### 6.3 敏感信息（P2）
- 百度网盘 `素材链接` 里的提取码 `pwd`：主表**不存密码**，`material_link` 存无密码 URL，密码单独存 `material_link_pwd` 并**密文存储**（复用 v3.1 的 Fernet 密钥体系）。
- 导入原始文件的内部批注在解析时丢弃，不落库、不进审计日志。

### 6.4 图片导入策略（P2）
- `素材链接` 是网盘地址，无法直接抓图。**导入阶段不自动下载封面/剧照**，导入后在剧目详情人工补传（走现有 MinIO 上传）。
- 可选后台任务「按名称匹配网盘 → 补图」作为后续迭代，不阻塞导入主线。

### 6.5 权限与审计（P0）
- 剧目 CRUD 受 RBAC data_scope 约束：`operator` 仅见自己创建的剧目（`created_by=自己`），`admin/publisher/material` 见全量。
- 导入/更新/删除写审计（复用 `audit_service` 的 `trace_id`），满足「可溯源」。

## 八、验收标准（DoD，可证伪）

1. **导入 diff**：用筛选表导入到**空库** → 全部判 `new`；再导一次 → 全部判 `update`（或 `unchanged`），确认 UI 列出「新增 N / 更新 M」，未勾选项不落库。
2. **询问更新**：重复导入时，不点确认则库中数据**零变化**；点确认后仅勾选项更新。
3. **唯一 ID**：每次导入/新建生成不重复的 `DR-xxxxxxxx`。
4. **发布联动**：选剧目发布 → 剧情简介自动填充 → 一键生成素材 → `PublishTask.material_id` 有值、话题含剧目题材标签。
5. **一剧多号**：同一剧目可关联多个视频号；视频号详情与剧目库双向可查。
6. **权限审计**：operator 只见自己创建的剧目；每次导入/更新有 `trace_id` 可溯源。
7. **封面/剧照**：剧目详情可上传/多传/拖拽排序封面与剧照，存 MinIO object key，不落主表二进制。

## 九、待评审确认点

1. **唯一 ID 格式**：`DR-<8位HEX>` 还是裸 UUID？（默认推荐 DR- 前缀）
2. **去重主键**：仅 `name` 唯一，还是按三元组？（筛选表 name 全唯一，故默认 name）
3. **剧情简介来源**：筛选表无 `剧情简介` 列，该字段由**人工在剧目详情录入**，还是导入后接一个「按名称/素材生成简介」的后台任务？（建议人工录入 P0，生成简介 P2）
4. **封面/剧照**：确认导入阶段不自动抓图、由人工补传？（推荐，避免卡死导入）
