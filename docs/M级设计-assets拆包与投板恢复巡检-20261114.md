# M 级设计先行：assets.py 拆包 ＋ 投板崩溃恢复巡检（2026-11-14，ISSUE #372）

> §5 口径：「各自先出设计方案再动代码，改动必须过三道门」。本文即两份设计。
> 现状实测：`backend/app/api/assets.py` **13,885 行、55 条路由**；已外移先例＝`asset_serializers.py`（11-13 批，5 序列化器）＋`asset_prompt_elements.py`（服务层）。

## 一、assets.py 按域拆包

### 1.1 切法：router 聚合，域文件平级

```
app/api/assets/
  __init__.py          # 聚合：router = APIRouter(); include 各域（对外 import 路径不变！）
  deps.py              # 共享依赖：_as_uuid/_split_ids/角色闸/REVIEW_PASSED_STATES 等小件
  summaries.py         # /assets/summaries ×8 ＋ review 相关
  prompt_elements.py   # /assets/prompt-elements ×6（F36 边界 5744-6260，最独立先切）
  productions.py       # /assets/productions ×5 ＋ /produce ＋ 试产 trial-verdict
  outputs.py           # /assets/outputs ×5 ＋ 交付包
  import_upload.py     # /assets/import ×3 ＋ /upload ×2
  jobs_analyze.py      # /assets/jobs ×2 ＋ analyze ×2 ＋ resolve
  misc.py              # categories/risk-lexicon/hook-codes/frames/download 等 ×12
```

### 1.2 为什么这样切（判据）
- **对外零破坏**：`app/api/assets/__init__.py` 聚合出同名 `router`，`main.py` 的
  `from app.api.assets import router` 一字不改——拆包过程任何一步可停在中间态（git revert 即回）。
- **prompt-elements 先切**：F36 已把该段边界钉死（5744-6260），且它只依赖
  `asset_prompt_elements` 服务＋guess 缓存表，是全仓耦合最低的一块；G-1 守卫的
  钉住用例（6226 commit 链）跟着搬家，搬完守卫必须仍绿（SET_LOCAL 名单按 key 匹配 file，
  **搬完要同步改 `SET_LOCAL_TIMEOUT_EXEMPTS` 的文件名**——这是拆包最容易漏的一处，写死在验收里）。
- **helper 不下沉**：`_call_autoclip`（4397）等被 5 个域共用的先留 `deps.py`，
  避免"拆包顺手重构行为"——拆包与重构分刀。

### 1.3 施工序（每步独立过三道门）
1. 建包壳＋`__init__` 聚合，assets.py 原样挪进 misc.py（行为零变，先验证聚合机制）；
2. prompt_elements.py 第一刀（含 G-1 名单同步）；
3. summaries/productions/outputs 三刀（每刀一个 commit）；
4. import_upload/jobs_analyze 收尾；deps.py 最后清。

### 1.4 风险与保险
- **最大风险＝循环 import**：域文件互引 helper。保险＝helper 只准从 deps.py/services 引，
  域文件之间禁止互引（CI 用 python -c import 冒烟逐文件验）。
- **现网部署**：backend/ 目录变 → 全量重建镜像（14 容器），照旧走部署链＋冒烟 8/8。
- **回滚**：每刀独立 commit，任何一刀红 → revert 该刀，聚合壳不受影响。

## 二、投板崩溃恢复巡检

### 2.1 问题（§5 原话：进程重启后 asset_jobs/在板任务的收口巡检目前靠人工再点一次）
- 投板＝建任务→轮询出片→下载落桶，一段几十分钟的活，跑在 **backend 进程内协程**；
- 进程重启（部署/崩溃/OOM）→ 轮询协程死透，`asset_jobs` 里 running 行**永远挂着**，
  在板 tid 没人收：钱已花的成片躺在豆包板上无人下载，一线只看到"投板中"不动。
- 11-13 163 内存雪崩那次就是活体：41 容器停摆重启后，靠人肉「只回收」补点。

### 2.2 设计：启动巡检 ＋ 周期心跳双钩子
```
app/services/asset_dispatch_recovery.py
  scan_orphan_jobs(db) -> list[RecoverPlan]
    # 判据：asset_jobs.status=running 且 kind∈{dispatch,produce} 且 updated_at 超阈值
    #       （阈值＝_call_autoclip 超时链顶 900s × 1.5 ≈ 1350s，避开活着的长任务）
    # 分型：
    #   A 有 tid 无产物 → RecoverPlan(recover_only)：复用现「只回收」口（不花钱）
    #   B 无 tid（建单阶段死）→ 标 failed＋人话原因「进程重启打断，单未投出」
    #   C 有产物未落库 → 补下载落库（幂等，走既有落桶链）
  recover_job(job, plan)  # 全部复用现有函数，不自写第二套（4495 _job_endpoint 口径）
```
- **启动钩子**：`main.py` lifespan 起一个后台任务跑 scan（延迟 60s 等容器就绪）；
- **周期心跳**：beat 每 15 分钟扫一轮（复用现有 celery beat，不加新 worker）；
- **人工可见**：恢复动作全部写 `audit_logs`（action=`asset.dispatch.recovered`，
  带 plan 类型），任务条/台账「提醒」列显示"进程重启后已自动回收 N 段"；
- **闸门**：恢复器只许调「只回收/标失败/补落库」三种**零花钱**动作——重投/重出永远留给人
  （号池一发即烧，机器不许自作主张烧第二次）。

### 2.3 验收
- 单测：三型 A/B/C 各造一条孤儿 job，跑 scan→recover，断言只回收口被调、audit 落行、不碰 produce；
- 集成：模拟"协程半途被杀"（patch 轮询函数抛 CancelledError），重启钩子能收；
- 现网：部署后人为重启 clip-backend，一条在板任务在 15 分钟内被自动回收（真数据零花钱验证）；
- 三道门照旧。

## 三、排期建议
- 拆包：刀①壳＋刀②prompt-elements 可下轮即做（半天/刀）；三刀③需一轮完整回归；
- 恢复巡检：独立开发项，估 1 天（含单测与现网演练）；与拆包无依赖，可并行。
