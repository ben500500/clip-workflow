# 任务内真分片 · 工程方案（立项评审稿）

> 2026-11-27 · 依据 relay/1120-clip-workflow-slice F108-F113 量化证据 + 112 pc=1/2 受控 A/B 实测
> 定位：**改造清单与成本评估，本文档不含任何代码改动**；立项后才排期实施。

## 1. 问题与收益

现状（F109 已从代码定死）：任务原子、创建时不切分；节点内唯一并行旋钮是 `--product-concurrency`（1..4）。
慢节点风险（用户原话「如果有某个节点的性能特别差，那就会出现明显的瓶颈」）已被 F108/F110 实证：
71+ 成品的大任务（5.3%）吃掉 75.2% 节点分钟，单条平均 82.7 分钟，全部阻塞在单节点单槽位上。

**量化收益（F113）**：91 成品任务（574MB 源，92:10）阶段分解——下载 0.1%、角标预叠 3.7%、
**切片编码 95.4%**、上传 0.8%。真分片收益几乎完全取决于编码占比：

| 分片方案 | 墙钟系数 | 91 成品任务 | 代价 |
|---|---|---|---|
| k=3，仅切片分片 | 0.446（2.24×） | 88min → 约 37min | 每节点各拉一次源片（574MB–1GB） |
| k=3，预叠加也分片 | 0.372（2.69×） | 88min → 约 32min | + k 次整片角标重编码 |

## 2. 改造清单（六项，按依赖序）

### 2.1 任务切分器（后端，新组件）
- 创建任务时按 `outputs_total` 与在线节点容量把成品块（候选组/变体组，**不可跨组拆**）切成 k 份，
  生成 k 个「分片任务」行（新表或 slice_tasks 加 shard 字段：parent_task_id/shard_index/shard_total）。
- cutlist 静态切分：按成品块边界切文本（引擎按行消费 cutlist，天然可切）；钩子 random 预选列表同步切块。
- 复杂点：random 模式变体间的「尽量不同钩子」预选逻辑要按块保持多样性（F24 语义）。

### 2.2 成品级租约与卡死巡检（worker + 后端）
- 现状 claimLoop/stuckTaskLoop/TaskTimeout 全是**任务级**：分片后一条分片任务=一个自然任务行，
  租约/心跳/卡死判定自动继承任务级语义——**这是选「分片=子任务」形态的最大理由**，无需改 worker 租约。
- 需新增：父任务聚合视图（进度=Σ分片已完成成品/Σ总成品）、父任务取消传播（cancel 一个父任务 →
  逐分片走现有 cancel/retry 出口，X14 的 PEL 语义自动生效）。

### 2.3 跨节点源片获取（worker）
- 现状每节点任务开始时拉一次源片；分片 k=3 → 3 次下载（574MB–1GB，千兆内网 3-10s/GB，可接受）。
- 可选优化：节点本地源片缓存（`temp/<source_md5>` 命中跳过下载）——非必需，二期。

### 2.4 跨节点成品去重与聚合（worker + 后端）
- 现状断点续传基线按「任务临时目录」；分片后每分片独立临时目录，**天然无冲突**；
  唯一要管的是输出文件命名：成品名带 -vN/-shardK 后缀防撞（已有 variant 后缀机制可复用）。
- 父任务 outputs_done/outputs_total 聚合回调：分片任务回调时上抛父任务，聚合层去重计数。

### 2.5 进度与前端语义
- slice_tasks 列表：父任务显示聚合进度（progress_message 标注「分片 1/3」）；
  Redis 进度 hash 按 parent 聚合；Slack/通知语义不变（父任务终态才发）。

### 2.6 调度策略与兜底
- k 的取值：min(在线节点数, ceil(outputs_total/单节点饱和成品数))，且 outputs_total < 8 不分片（开销>收益）；
- 分片派发用现有 target_node_id 直投 + 公共流兜底（某节点离线时分片自动回公共流）；
- 慢节点拖后腿（F110 实证）的缓解：分片按节点历史 s/成品加权分配成品块（worker_nodes 已有数据可算）。

## 3. 成本与风险

| 项 | 评估 |
|---|---|
| 开发量 | 后端切分器+聚合 2-3 天；前端进度视图 1 天；联调+故障注入测试 2 天 ≈ **1 周** |
| 兼容性 | 分片=子任务形态完全复用现有租约/取消/重试/PEL，**不动 worker 核心状态机**（最大风险点消失） |
| 流量成本 | k 倍源片下载（内网，实测 0.1% 任务墙钟，可忽略） |
| 一致性风险 | cutlist 切块错位 → 输出重复/缺失：需一个「分片 cutlist 校验器」（切块后逐行断言全集=原子集并集） |
| 语义风险 | 「任务」粒度变化影响用户认知（列表里见 1 条还是 k+1 条）——建议父任务折叠显示 |

## 4. 与受控 A/B 的关系

112 pc=1 vs pc=2 A/B（本轮实测，数据见 relay log 回填）回答「节点内并发 vs 节点间分片」的边际收益排序：
- 若 A/B 显示 pc=2 墙钟收益显著（≥1.5×），优先推 pc 配置（零开发），分片立项顺延；
- 若 pc=2 收益平平（线程争用抵消），则分片是唯一大杠杆，立项优先级提升。

## 5. 立项建议

**建议立项，排期放在 pc A/B 结论之后**。首期范围收窄为：仅 fast/dedupe 两模式 + 无钩子任务分片
（钩子 combine 链缓存语义复杂，二期），k 上限 3，父任务折叠显示。验收判据：同一 91 成品任务
k=3 墙钟 ≤ 42 分钟（2.2×），且三节点成品全集与单节点跑的成品集合一一对应（文件名+时长+md5 抽检）。
