## 二、核心契约差异（role spec / 文档 vs 线上真实）

### D1 — 列账号接口写错
- role Step1：`GET /wechat-dl/accounts` → **404**（该路由根本不存在）
- 线上真实：`GET /publish/video-accounts` → 200，返回账号数组
- 文档 F1 写法正确，role spec 此处照搬错了。
- 返回字段实测（节选）：
  ```json
  {"id":"b3c21516-...","account_name":"帷幕小剧场","platform":"wechat_channel",
   "profile_id":"29033bb6-...","enabled":true,"operator_id":"0d40da91-...","wxid":"sphpP5nTaJoqtZe"}
  ```
- ⚠️ 文档 F1 示例写 `"platform":"wechat"`，**线上实际值是 `wechat_channel`**（文档细节不准，但不影响流程）。

### D2 — 发起下载接口写错
- role Step4：`POST /wechat-dl/tasks` → **405**（该路由仅支持 GET 列表/批量状态）
- 线上真实：`POST /wechat-dl/import` → 创建下载任务，返回：
  ```json
  {"task_id":"...","status":"pending","source_type":"self_owned","message":"已创建下载任务并进入 wechat_dl 队列"}
  ```
- 必填字段：`source_url`（空 body→422；有 source_url→建任务）。`source_type` 可选（默认 self_owned）、`project_id` 可选。

### D3 — tus 上传「创建会话」端点写错
- role Step12：「先 `POST /upload` 创建上传（201）」
- 线上真实：
  - `POST /upload` = **直接单文件上传**（multipart `file` + `project_id`），**不是** tus 会话创建。这正是先前修进度条的那个接口。
  - tus 会话创建实为 **`POST /upload/resume`**（body `file_name`+`file_size`+`chunk_size`），返回 `{"id":"<upload_id>","offset":0,...}`。
  - 后续：`PATCH /upload/{upload_id}` + `Upload-Offset` 头 + raw bytes 续传 → `POST /upload/complete`。
- 即 role 把"直接上传"和"tus 会话创建"搞混了。tus 流程本身是对的，只是创建端点名应为 `/upload/resume`。

### D4 — video_account_id 非必填（文档 F3 不一致）
- `POST /publish/tasks` 空 body → 422 仅报 `output_id`、`platform` 必填，`video_account_id` 未报必填。
- 说明发布任务可**不传 video_account_id 而由系统自动推导**（PR #177 已修复 operator_id 自动推导，video_account_id 同理可能可省）。文档 F3 把它列为必填，属于文档与实现的偏差（不阻塞，但自动化脚本照文档硬传会多此一举）。

## 三、问题清单（按优先级）

### 🔴 P0 — 扫码登录 `POST /publish/login/qr` 返回 502（Step3 系统性阻断）

**现象**：`POST /publish/login/qr` → 502；后端日志：
```
WARNING app.services.login_qr_service:[qr_spike] profile(...) 抽 QR 失败：
  BrowserType.connect_over_cdp: connect ECONNREFUSED 172.18.0.6:9224
POST /api/publish/login/qr HTTP/1.1" 502 Bad Gateway
```

**根因（已定位）**：端口错配。
- rpa_worker 容器内 Chromium 实际监听 **`--remote-debugging-port=9223`**（仅此一个实例在跑）。
- 但 `login_qr_service` 经 `_resolve_profile_port` 解析出 **host=`rpa_worker`、port=`9224`**：host 来自 `CHROME_DEBUG_HOST=rpa_worker`(.env)；port 来自 `multi_operator` 的 **Redis 端口池**（基址 `PORT_BASE=9223`，给该账号分配了 9224）。
- 结果：连 9224 被拒 → QR 抽取失败 → 502。
- 回退链 `PublishProfile.chrome_debug_port` 默认 9222，也不是 9223，所以回退也连不上。
- **影响范围**：系统性——所有账号都会中招（端口池分配的端口都没有对应 Chrome 监听）。

**修复建议（二选一，需你确认后再动）**：
1. **架构正确修法**：让 rpa_worker 为端口池分配的每个端口真正启动一个 Chromium（即 multi-operator 的 launch 逻辑应按池端口起 Chrome）。当前只有基址 9223 的 Chrome 在跑，池却分配了 9224+。
2. **快速解锁（单运营者场景）**：把该账号的调试端口重新指向实际在跑的 9223（修正 Redis 端口池 entry / route，或让 resolve_port 对该账号返回 9223）。注意需 `REDIS_PASSWORD` 才能改端口池。

> ⚠️ 本 Agent 在「对齐」阶段只诊断未修复；是否修复及用哪种方案，等你拍板。

### 🟡 P1 — role spec 三处接口路径错误（D1/D2/D3）
照 role spec 原样跑会在 Step1/Step4/Step12 立刻 404/405。建议把 role spec 按本报告二·D1–D3 修正（或统一以 `AUTOMATION_WORKFLOW.md` v1.1 为准，该文档这部分是对的）。

### 🟢 P2 — 文档细节偏差

- 文档 F3 把 `video_account_id` 列必填，实为非必填（可自动推导）。
- 以上不影响流程，仅影响断言严格度，建议在文档加注。

## 五、环境备注（自动化脚本须知）

1. **后端实际端口是 `:8001/api`**，不是文档写的 `:8000`；role spec 的 `http://<部署机>/api` 未带端口。
2. **从 Mac 直连 `192.168.1.163:8001` 返回 502（内网不通）**，自动化脚本必须：
   - 要么在 163 内部执行 HTTP 调用（`127.0.0.1:8001`），
   - 要么先建 SSH 本地端口转发（`ssh -L 8001:127.0.0.1:8001 ...`）再走 `localhost:8001`。
3. 鉴权用 `JWT_SECRET` 可签发 admin token（无需明文密码），适合自动化；长流程记得 `POST /auth/refresh` 续期（Cookie 无感刷新）。
4. **探测产生的无害脏数据**（已记录，不影响运行）：
   - 下载任务 `91019574-...`（source_url="x"）→ 已 `failed`，自然结束；
   - tus 会话 `b00ef1cb-...`（未传文件）→ 无副作用，会被清理。
