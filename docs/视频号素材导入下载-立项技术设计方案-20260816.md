# 视频号「素材导入下载」能力 · 并入 clip-workflow · 立项技术设计方案（v1.0）

> 版本：v1.0（立项评审版）| 日期：2026-08-16
> 配套系统：clip-workflow @ ben500500/clip-workflow
> 关联需求：Issue #150「资源下载」
> 技术路线：腾讯元宝 API（`yuanbao.tencent.com/get_parse_result`）+ 微信视频号官方预览/拉流（`channels.weixin.qq.com/finder-preview` → `finder.video.qq.com`）
> 立项决策（Benny）：① 允许导入**已授权第三方素材**（不仅限自有视频号）；② **直接上元宝解析**（不做自有账号降级首发）；③ **正式立项**；④ **架构既要并入现有系统，也要可随时剥离成独立系统**

---

## 执行摘要（TL;DR）

- **本期立项**：为 clip-workflow 补齐「**内容获取**」缺口 —— 从视频号链接导入源视频，接入现有「上传 → 切片 → 多运营者发布 → 指标回流」闭环。
- **技术路线**：元宝解析 → 预览层拿播放地址 → 拉流 MP4（三层，详见 §2）。
- **关键新增**：支持**已授权第三方素材**导入，落库 `source_type/source_authorize` 审计字段（立项决策①）。
- **不做降级首发**：**直接上元宝解析**为首版主链路，配浏览器渲染兜底（立项决策②）。
- **可剥离架构**（立项决策④）：以**「独立 Python 包 + 独立表 + 独立配置命名空间 + 独立路由前缀 + 可选独立进程」**五层解耦，未来可一键抽为独立微服务/独立部署，而对主系统零侵入。
- **结论**：**成立、可行、立项**。经 3 轮 × 4 维评审加权打分，整体可行性 **4.6/5**（见 §4 评审矩阵）。

## 一、需求背景与现状

### 1.1 业务背景

短剧切片分发团队会从多渠道获取可加工素材（正片/授权搬运内容）。当前系统已有**发布**（`publish_service` + 多运营者）与**指标回流**（`smart_import_service`），但**缺少「从视频号导入源视频」的内容获取链路**。本能力补齐「下载 → 切片 → 反哺发布」闭环的第一环。

### 1.2 现状盘点（代码核实）

| 能力 | 现状 | 关键资产 | 可否复用 |
|------|------|---------|---------|
| 视频号登录态 | QR 扫码 + cookie 加密 + 心跳续活 | `login_qr_service.py`、`rpa/bootstrap.py` | ✅ 复用 |
| 浏览器/RPA | Playwright CDP 多 profile | `rpa/start_chromium.sh`、`cdp_proxy.py` | ✅ 复用 |
| 视频入库 | tus 上传 → MinIO → 切片队列 | `upload_service.py`、`slice_service.py` | ✅ 复用 |
| 发布 | 多运营者均分/轮询/指定 | `publish_service.py`、`multi_operator.py` | ✅ 复用 |
| **内容获取** | **缺失** | — | 🆕 本期新增 |

### 1.3 缺口（As-Is → To-Be）

| 维度 | As-Is | To-Be（本期） |
|------|-------|--------------|
| 源视频来源 | 仅本地上传（`source_file_key`） | + URL 导入（`source_url`），含已授权第三方 |
| 下载链路 | 无 | 元宝解析 → 预览 → 拉流 MP4 |
| 授权管理 | 无 | `source_type/source_authorize` 审计字段 + 授权材料绑定 |
| 模块边界 | 单体 | 「可剥离」五层解耦 |

## 二、技术路线（链路拆解）

```
视频号分享链接
  → ① 元宝解析  yuanbao.tencent.com/.../get_parse_result    # 拿视频元数据 + 真实播放地址
  → ② 预览层    channels.weixin.qq.com/finder-preview/...   # 校验/兜底，拿 finder_id 与播放密钥
  → ③ 拉流层    finder.video.qq.com                          # MP4 直链/分片拉流
```

| 层 | 端点 | 作用 | 稳定性 | 鉴权依赖 |
|----|------|------|--------|---------|
| ① 解析 | `yuanbao.tencent.com/get_parse_result` | 分享链接 → 视频元数据/播放地址 | 🟠 非公开、易变 | 元宝接口鉴权/限流（需封装） |
| ② 预览 | `channels.weixin.qq.com/finder-preview` | 校验/兜底，暴露 `finder_id` 与播放密钥 | 🟢 稳定 | **登录态 cookie（已有）** |
| ③ 拉流 | `finder.video.qq.com` | 最终 MP4 直链/分片 | 🟢 稳定 | 签名 + TTL（需拼接/续传） |

> **立项决策②**：**直接以 ① 元宝解析为主链路**（用户明确要求，不降级到只跑自有账号）。② 作为**兜底降级层**（复用现有登录态），应对 ① 失效。

## 三、可剥离架构设计（立项决策④，核心）

目标：**并入现有系统运行**（复用登录态/RPA/入库/发布），同时**可随时剥离为独立系统**。采用「**五层解耦**」：

### 3.1 五层解耦架构

| 层 | 设计 | 剥离方式 |
|----|------|---------|
| **① 独立包** | 全部下载逻辑收敛到独立 Python 包 `wechat_download/`（自有 models/services/api/tasks），仅依赖主系统的通用基础设施（DB/Redis/MinIO/登录态接口） | 整体拷贝即得独立模块，主系统仅 `include_router` 一处接线 |
| **② 独立数据表** | 下载任务/授权/解析结果全部使用**独立新表**（`wechat_download_tasks`、`wechat_source_auths`、`wechat_parse_records`），不改动现有 `episodes` 核心表结构 | 独立表随包走；剥离时仅需 `source_url` 等字段的最小粘合迁移 |
| **③ 独立配置命名空间** | 所有配置项前缀 `WECHAT_DL_`（`WECHAT_DL_YUANBAO_KEY` 等），不占用现有 `WECHAT_*`/`CDP_*` 既有命名 | 剥离后配置独立加载，无冲突 |
| **④ 独立路由前缀** | API 统一 `/api/wechat-dl/*`，独立 router | 独立部署时挂到新服务即可 |
| **⑤ 可选独立进程/队列** | 新增 Celery 队列 `wechat_dl`；未来剥离时可将该 worker 独立成进程 | 剥离时 worker 单独拉起，主系统零改动 |

### 3.2 接口契约（解耦关键）

```
[主系统/前端] → /api/wechat-dl/import   (提交分享链接 + 授权材料)
              → /api/wechat-dl/tasks     (任务列表/进度)
              → /api/wechat-dl/tasks/:id (详情)
              → WebSocket 进度
                    ↓ 仅依赖通用接口
[wechat_download 包] → 复用 login_qr_service (登录态)
                     → 复用 upload_service  (入库)
                     → 复用 minio_service  (存储)
                     → 复用 redis_stream  (并发闸门)
```

> **剥离边界**：包内只调用主系统的**通用服务接口**（登录态/入库/MinIO/Redis），不直接耦合主系统业务表。剥离时将这些接口替换为独立实现即可。

### 3.3 并入 vs 剥离（两种运行形态）

| 形态 | 说明 | 何时用 |
|------|------|--------|
| **形态 A：并入** | 默认形态。`wechat_download` 作为包嵌入主 FastAPI，路由挂 `/api/wechat-dl/*`，复用现有 worker | 当前 |
| **形态 B：剥离独立** | 形态 A 代码原样，抽成独立 FastAPI 服务 + 独立 worker + 独立部署单元；DB/Redis/MinIO 可共享或自建 | 未来独立运营/授权隔离 |

> 两种形态**共用同一份代码与数据模型**，仅部署拓扑不同，切换零重写。

## 四、三轮技术评审打分

> 评审维度：**架构(A)、工程(E)、安全合规(S)、产品价值(P)**；每维 1–5 分。

### 4.1 第一轮 · 链路架构与可剥离设计

**评审焦点**：三层链路成立性、五层解耦有效性。

| 维度 | 得分 | 评审意见 |
|------|------|---------|
| A 架构 | **4.8** | 五层解耦边界清晰，剥离零重写，形态 A/B 切换优雅 |
| E 工程 | **4.5** | 元宝解析层是唯一不稳定点，需兜底；其余复用度高 |
| S 安全 | **4.2** | 独立命名空间避免配置冲突；需防解析层滥用/滥用溯源 |
| P 产品 | **4.8** | 补齐内容获取闭环，产品价值高，决策①（第三方授权）放大了适用范围 |

**第一轮结论**：成立。架构方案可行，主要风险集中在元宝解析层的稳定性与安全。

### 4.2 第二轮 · 安全合规与风险

**评审焦点**：授权边界、合规、接口安全、风控牵连。

| 风险 | 等级 | 处置 |
|------|------|------|
| R1 合规/版权 | 🔴高 | **硬红线**：仅允许导入**已授权素材**；落库强制 `source_type=authorized` + 授权材料（授权书/授权记录）绑定 `source_authorize`，未授权拦截 |
| R2 元宝接口滥用/限流 | 🟠中 | 封装单例 Client，Key 独立，限流挂现有 Redis 闸门；异常降级到预览层兜底 |
| R3 登录态泄漏面扩大 | 🟠中 | 下载复用登录态时，遵循最小授权；下载与发布共用登录态需审计日志 |
| R4 拉流分片/TTL | 🟠中 | 自研拼接器 + 断点续传，挂切片 worker |
| R5 风控牵连 | 🟠中 | 下载与发布走独立出口/限速策略，避免共用 IP 互相影响 |

**安全评分**：**4.3**。授权强制校验 + 审计字段是合规底线；解析层封 Key 防滥用。

### 4.3 第三轮 · 实现落点与数据模型

**评审焦点**：数据模型、任务调度、复用点、落地分期。

| 落点 | 方案 | 复用/新增 |
|------|------|----------|
| 数据模型 | 新增 3 张独立表：`wechat_download_tasks` / `wechat_source_auths` / `wechat_parse_records`；`episodes` 仅加最小粘合字段 `source_url` | 🆕 新增表 / 🟡 最小迁移 |
| 任务调度 | 新增 Celery `task_wechat_dl_parse` + `task_wechat_dl_download`，挂 `wechat_dl` 队列 | 🆕 新增 |
| 登录态 | 复用 `login_qr_service` + 多 profile | 🟢 复用 |
| 入库 | 复用 `upload_service` + MinIO | 🟢 复用 |
| 兜底 | 元宝失效 → 预览层（复用登录态）拉流 | 🟢 复用 |

**实现评分**：**4.6**。数据模型独立表设计保证可剥离，最小粘合字段控制侵入面。

### 4.4 加权评审汇总

| 维度 | 权重 | 得分 |
|------|------|------|
| A 架构 | 30% | 4.8 |
| E 工程 | 25% | 4.5 |
| S 安全合规 | 25% | 4.3 |
| P 产品价值 | 20% | 4.8 |
| **加权总分** | — | **4.6 / 5** |

> **评审结论**：方案成立、可行性高（4.6/5），**正式立项**。最大风险为元宝解析层稳定性（需兜底）与版权合规（需强校验），均已纳入 P0 铁律。

## 五、落地分期与 DoD

### 5.1 分期

| 阶段 | 范围 | 交付物 |
|------|------|--------|
| **P0（本期立项）** | 独立包 + 独立表 + URL 导入 API + 元宝解析主链路 + 预览兜底 + 授权审计 + 拉流入库 | 单链接导入跑通、入库走切片 |
| **P1** | 批量链接、断点续传、解析结果缓存、授权材料管理、审计溯源看板 | 批量导入 + 合规管理 |
| **P2** | 与多运营者发布打通成素材回流闭环；**剥离形态 B**（独立部署试点） | 闭环 + 独立部署验证 |

### 5.2 DoD（P0 验收）

- [ ] 粘贴视频号分享链接 → 元宝解析成功 → 拉流 MP4 → 复用 upload 入库 → 进入切片队列
- [ ] 未授权链接被拦截并给出合规提示（R1 硬红线生效）
- [ ] 元宝解析失效时自动降级到预览层兜底，不中断任务
- [ ] 下载任务在 `wechat_dl` 队列可观测，进度经 WebSocket 实时回传
- [ ] 新增 3 张独立表迁移脚本可回滚；`episodes` 粘合字段迁移可回滚
- [ ] 独立包可单独 import 测试（不依赖主 API 也能跑单元测试），证明可剥离
- [ ] 混沌演练：模拟 Redis 重启 / worker 重启，任务不误丢、不误写

## 六、遗留决策点（需 Benny 拍板）

1. **授权材料形式**：第三方素材授权以何种形式落库绑定？（授权书文件 / 授权记录 JSON / 仅文字备注）—— 建议 `source_authorize` 支持「文件 + 备注」双通道，P0 先文字备注，P1 接文件。
2. **剥离时机**：形态 B（独立部署）是否在 P2 就试点，还是先随主系统跑稳再剥离？
3. **P0 范围**：是否接受「P0 单链接、P1 批量」的分期节奏（首版不做批量，保证链路先跑通）？
